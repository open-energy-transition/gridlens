# AGENTS.md

Context for an AI coding agent (Claude, Codex, Cursor, or similar) picking
up this repository with no other context. Read this file first, in full,
before making any change.

## What this is

GridLens is a public, open-source, zero-backend web app tracking real-world
adoption of energy system modelling tools (PLEXOS, PyPSA, and dozens more)
by institutions worldwide — which organization, in which country, uses
which tool, for what grid decision, with evidence. Built and maintained by
Open Energy Transition. It fully replaces the earlier `esm-usage-catalog`
Streamlit prototype as the canonical public repo for this dataset + app.

Two things evolve independently and both matter equally:
1. **The dataset** — contributions of new/corrected/removed organizations.
   This is expected to be the main ongoing source of change, including from
   scheduled LLM agents (see "Weekly automated research" below).
2. **The app** — UI, features, bug fixes, performance.

## Zero-cost constraint (non-negotiable)

No backend, no database, no paid API keys, no server-side anything.
Everything runs client-side in the browser against a static bundled JSON
file. Any proposed feature that would require a backend or a paid service
should be redesigned to work client-side first, or declined.

files — Claude Code (and compatible agents) auto-attach a subdirectory's
AGENTS.md the moment they read any file in it, so you'll see those even if
you don't navigate here first. They're short; the full reference docs they
point to (DATA_SCHEMA.md, RESEARCH_PLAYBOOK.md) are not auto-loaded — go
read those in full before editing data.

## Commands

```bash
npm install
npm run dev              # local dev server, http://localhost:5173
npm run build             # tsc -b && vite build — must be 0 TypeScript errors before committing
npm run test              # vitest — pure-logic regression tests (filters, choropleth bucket math)
npm run validate-data     # check data/raw/*.csv before syncing
npm run sync-data         # validate, then regenerate catalogue_merged.csv + src/data/catalogue.json
```
Node version is pinned in `.nvmrc`. CI (`.github/workflows/ci.yml`) runs
validate-data → sync-data (failing if that produces an uncommitted diff) →
test → build → lint on every push/PR — all four must pass.

## Workflow: contributing a dataset change

1. Read `data/DATA_SCHEMA.md` (which raw file, which columns, which enum values).
2. Add/edit/remove the row in the correct `data/raw/*.csv`. Never hand-edit
   `data/catalogue_merged.csv` or `src/data/catalogue.json` — they're
   generated and will be overwritten.
3. `npm run sync-data` (runs validation first, then regenerates).
4. Add a dated entry to `src/data/changelog.json` per
   `CHANGELOG_MAINTENANCE.md` — **every** organization added/removed/
   reclassified gets one, in the same change as the data edit. Country/app
   feature changes do NOT belong there (see that file for the full
   add/remove/reclassified/coverage taxonomy, and why — it's modeled
   directly on artificialanalysis.ai's own changelog, which is 100% data
   events, zero UI announcements).
5. `npm run build` — confirm it's still clean.
6. Commit the raw CSV diff + regenerated `catalogue_merged.csv`/
   `catalogue.json` + the changelog entry together, in one commit.

## Workflow: contributing an app change

Standard React/TypeScript work. Conventions already established in this
codebase, follow them rather than introducing a new pattern:
- Tailwind v4 utility classes throughout, no CSS modules/styled-components.
  Brand colors/fonts come from the OET style guide (Oswald display font +
  Plus Jakarta Sans body font, red `#e31937` / sage `#7c9885` — see
  `tailwind.config`/`index.css` `@theme` block, and the
  `react-tailwind-v4-brand-restyle`-style conventions already in the code).
- Shared chart/UI colors live in `src/lib/colors.ts` — don't hardcode a new
  hex value in a component; add it there if a genuinely new one is needed.
- Every new nav page: add to the `Section` union in `types.ts`, add a file
  under `src/sections/`, wire it into `App.tsx`'s section switch, add a nav
  entry in `Sidebar.tsx`.
- `npm run build` must show 0 TypeScript errors before any commit.
- After a UI change, actually look at it (a headless browser + a real
  screenshot/DOM query, not just "the code looks right") before calling it
  done — several bugs in this app's history (a map/graticule misalignment,
  a 768px overflow, invisible low-count map colors) were only caught this
  way, not by reading the diff.

## Non-negotiables

- **No fabricated data.** An organization/claim without a real, checkable
  source URL does not go in the dataset — see `data/DATA_SCHEMA.md`'s
  evidence standards.
- **No backend, no paid APIs, no API keys.** Client-side only.
- **Changelog discipline.** Dataset changes get a changelog entry in the
  same change; app/UI changes do not.
- **Evidence over inference.** The organization's own first-person document
  beats a vendor case study beats an inferred/assumed usage.

## Weekly automated research (intended future state)

This repo is designed so a scheduled LLM agent (e.g. a weekly cron job) can
run `research/RESEARCH_PLAYBOOK.md`'s loop autonomously: pick a gap from
`research/world_country_checklist.csv`, search using the documented
techniques, append verified findings to `data/raw/*.csv`, update the
changelog, validate, sync, build, and open a pull request. If you are that
agent: open a PR rather than pushing to main directly, and keep the PR
scoped to one wave's findings (not a mix of dataset changes and unrelated
app changes) so a human reviewer can evaluate the evidence quickly.

## Design history

The UI design (OET brand restyle, Artificial-Analysis-style landing page,
the GridLens lens-over-aperture logo, the choropleth map fixes) and the
dataset's research methodology both have a lot of accumulated reasoning
behind specific decisions. If something looks like it could obviously be
done a simpler way, check `research/history/` and the git log before
assuming it's an oversight — several past fixes (the sqrt color scale, the
graticule-inside-ZoomableGroup fix, the changelog's data-only scope) were
deliberate corrections of a less-obvious bug.
