# Data schema

GridLens's entire dataset lives in **one file**: `data/raw/catalogue.jsonl`
(JSON Lines — one JSON object per line, every organization/tool pairing,
across both PLEXOS and every other energy-system-modelling tool). It gets
validated by `scripts/validate_dataset.py` against `data/schema.json`,
then regenerated by `scripts/sync_dataset.py` into `data/catalogue_merged.csv`
(human-readable) and `src/data/catalogue.json` (what the app actually
imports — never edit this JSON by hand, it's generated).

```
data/raw/catalogue.jsonl ──▶ scripts/sync_dataset.py ──▶ data/catalogue_merged.csv ──▶ src/data/catalogue.json
         ▲
         │ validated against
         │
data/schema.json
```

## Why one file, and why JSONL (not CSV)

This used to be two CSVs with different schemas (a PLEXOS-specific one and
a generic one), translated into the app's format by `sync_dataset.py`. That
split added a translation layer for no real benefit — adding a new
organization never genuinely needs two different formats, it just needs one
consistent record. It's now a single file in the app's near-final shape, so
there's no origin-specific translation logic left.

JSONL instead of CSV specifically because an LLM agent is the primary
contributor here, and CSV is fragile for exactly the kind of text this
dataset is full of: multi-clause free text with embedded quotes and commas
(`exact_snippet_or_quote`, `notes`). One mis-escaped quote in a CSV silently
shifts every column in every following row; one malformed JSON line fails
to parse *at that line* and nowhere else. Appending a new finding is "add
one line" either way — JSONL just fails safely when something's off, and
LLMs are measurably more reliable at emitting syntactically valid JSON than
correctly-quoted CSV.

`data/catalogue_merged.csv` still exists as a **generated** human/spreadsheet-
readable mirror — CSV is fine for a read-only, machine-produced artifact;
it's only risky as something an agent hand-edits.

## Adding, correcting, or removing an organization

**Append one JSON object as one line** to `data/raw/catalogue.jsonl`. Use
an existing line as a template, or see the field reference below. Required
fields are enforced by `data/schema.json`; `scripts/validate_dataset.py`
checks against it. **Never edit `catalogue_merged.csv` or `catalogue.json`
directly** — they're overwritten by `scripts/sync_dataset.py`.

After any edit:
```bash
npm run validate-data   # checks data/raw/catalogue.jsonl against data/schema.json
npm run sync-data       # validates, then regenerates the two generated files
npm run build           # confirm the app still builds
```
Then add a `src/data/changelog.json` entry (see `CHANGELOG_MAINTENANCE.md`)
if the change is dataset-content (new/removed/reclassified organization),
not for pure data-quality fixes like filling in a blank `institution_category`.

## `data/raw/catalogue.jsonl` field reference

The machine-checkable version of this table is `data/schema.json` — treat
that as authoritative if the two ever disagree; this is the prose
explanation of *why*.

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Unique, stable identifier, e.g. `ORG-0001` or `ESM-0001`. **Never renumber or reuse an existing id** — research notes elsewhere in the file cross-reference ids by exact string (e.g. "same org, see ORG-AFME-0010"), so renumbering silently breaks that trail. |
| `institution_name` | yes | The institution's name, in English where there's a common English name, otherwise its own name. |
| `institution_category` | no (but fill it in) | One of the enum values in `data/schema.json` (`utility_iso_rto`, `utility_tso`, `utility_generation`, `utility_distribution`, `consultancy`, `vendor`, `academic_research`, `think_tank`, `industry_association`, `government_agency`, `government_regulator`, `international_body`, `development_bank`, `ngo_foundation`, `energy_company_diversified`, `project_developer`, `other`). Left blank only for older migrated rows that predate this field — `validate_dataset.py` warns (not errors) on blank, but fill it in for every new entry: it's what Grid Decisions falls back to inferring from when `decision_type` isn't set directly. |
| `official_website` | no | Institution's homepage. |
| `country_label` | yes | Canonical country name. **Check the alias list in `scripts/validate_dataset.py`** (e.g. "USA" vs "United States") before using an unfamiliar spelling — a split spelling silently splits one country into two choropleth entries on the map. Use `"Multi-country (...)"` for regional bodies (e.g. ENTSO-E, WAPP). |
| `tool_name` | yes | e.g. `PLEXOS`, `PyPSA`, `NEWAVE`, `DIgSILENT PowerFactory`. |
| `tool_category` | no | One of the enum values in `data/schema.json` (`production_cost_uc`, `capacity_expansion`, `planning_expansion`, `market_simulation`, `energy_system_optimization`, `forecasting`, `distribution_planning`, `other`) — the model's *technical class*. Not the same axis as `decision_type` below (that's the *purpose*, this is the *kind of model*). |
| `tool_explicitly_named` | no | `true`/`false` — whether the source explicitly names this tool (vs. a generic "energy system model"). |
| `role` | yes | One of: `direct_user`, `commissioner`, `consultant_modeler`, `research_user`, `subject_of_study`, `qa_reviewer`. See role definitions below. |
| `use_case` | yes | What the tool is actually used for, as specifically as the evidence allows. This is what Grid Decisions classification reads — a generic one-liner gets you a generic (and honestly-labeled "inferred") decision type; a specific sentence with real detail gets classified from the text itself ("documented"). |
| `decision_type` | no | One of the enum values in `data/schema.json` (see the Derived field section below). **Leave blank unless you have real evidence for it** — `scripts/sync_dataset.py` infers one automatically otherwise. |
| `decision_basis` | no | **Leave blank** — `scripts/sync_dataset.py` sets this to `documented` or `inferred` automatically depending on whether you set `decision_type` yourself or it was inferred. Don't hand-set this to `documented` unless `decision_type` is genuinely backed by `use_case`/`exact_snippet_or_quote`. |
| `evidence_strength` | yes | `HIGH`, `MEDIUM`, or `LOW` — set this directly based on the evidence standards below (first-person document = HIGH, vendor case-study/third-party mention = MEDIUM, weak/indirect = LOW). |
| `source_type` | no | e.g. `research_finding`, `news_release`, `academic_paper`, `procurement_notice`, `official_methodology`. |
| `source_title` | no | Title of the source document. |
| `source_date` | no | Date of the source (free text, not strictly validated). |
| `source_url` | yes | A working URL to the primary evidence (the organization's own document/page preferred over a vendor case study). |
| `exact_snippet_or_quote` | no (but strongly preferred) | A direct quote supporting the claim — see evidence standards below. |
| `why_it_supports_the_claim` | yes | One sentence connecting the quote/source to the claim being made. |
| `status` | yes | `confirmed` (syncs into the app), `candidate` (not yet verified, excluded), `rejected` (evidence didn't hold up, excluded — kept in the file, not deleted, so a future wave doesn't repeat the same dead-end search), `gap_confirmed` (actively searched, genuinely no evidence found). |
| `historical_or_current` | yes | `current` or `historical` — is the use still active, or a past engagement? |
| `batch_id` | no | Free-text provenance tag for which research pass/session found this row, e.g. `weekly_llm_scan_2027w03`. Shown to end users as the record's dataset origin in the Records table. |
| `notes` | no | Free text: caveats, the evidence reasoning, cross-references to other `id`s, anything a reviewer should know. PLEXOS-catalogue-origin rows carry a lot of research narrative here — keep that convention, it's valuable audit trail. |

### Role definitions

- `direct_user` — the organization runs the tool itself for its own planning/operations.
- `commissioner` — the organization paid for/requested a study but didn't build the model itself.
- `consultant_modeler` — the organization built/ran the model as a vendor for someone else.
- `research_user` — academic/research use, typically co-equal with a commissioning org rather than a hired vendor.
- `subject_of_study` — the organization's grid/system was modeled in someone else's study; it did not commission or run anything itself. Use sparingly — only when there's no plausible commissioner/direct-user role for the same organization.
- `qa_reviewer` — reviewed/validated someone else's tool-based study.

For a rejected lead, use `status=rejected` rather than a `role` value — keep the row (don't delete it) with the evidence-review reasoning in `notes`.

## Derived field: `decision_type` / `decision_basis`

These two fields answer "what grid decision is this tool actually used
for" — a different axis from `tool_category` (the model's *technical
class*) or `role` (the organization's *relationship* to the tool). They
are **computed by `scripts/sync_dataset.py`** when left blank — see
`resolve_decision()` in that script for the actual logic.

`decision_type` is one of: `Capacity & Resource Planning`,
`Unit Commitment & Dispatch`, `Market Operations & Price Formation`,
`Transmission & Network Planning`, `Renewable Integration & Decarbonization`,
`Forecasting & Scenario Analysis`, `Policy & Regulatory Analysis`,
`Academic & Research Studies`, `Independent & Commissioned Studies`,
`Other / General Modeling`.

Resolution order, per record:
1. If you set `decision_type` directly in `catalogue.jsonl`, it's trusted
   as-is and marked `decision_basis="documented"`. Do this when you have
   real evidence for the specific decision purpose.
2. Otherwise, if `use_case` is specific (not just the generic role-based
   fallback sentence), it's classified by keyword rules against that text
   — still `decision_basis="documented"` even if no keyword matches
   (real evidence exists, it's just unclassified, landing in
   `Other / General Modeling`).
3. Otherwise (no `decision_type`, no specific `use_case` — i.e. all we
   know is the organization's role and sector), it's inferred from
   `institution_category` as a last-resort proxy, marked
   `decision_basis="inferred"`. **This is not a documented claim** —
   an organization's sector is a reasonable guess at what it uses a tool
   for, not evidence. Keep this distinction visible in the UI (see
   `GridDecisions.tsx`'s "Documented"/"Inferred" badges); don't silently
   upgrade an inferred row to look documented.

If you tighten a historical row's classification later (e.g. by writing a
real, specific `use_case` for a row that only ever had the generic
role-based fallback), the next `sync_dataset.py` run will automatically
pick it up as `documented` — you don't need to touch `decision_basis`
yourself.

## Evidence standards

1. **First-person evidence beats third-party mentions.** An organization's
   own planning document, press release, or procurement record stating it
   uses a tool outranks a vendor's case-study page naming the same
   organization as a client.
2. **A direct quote is worth more than a paraphrase.** Prefer filling
   `exact_snippet_or_quote` over summarizing in `why_it_supports_the_claim`
   alone.
3. **A rejected lead stays in the file as `status=rejected`**, not deleted —
   this prevents a future wave from re-investigating the same dead end from
   scratch. See `research/RESEARCH_PLAYBOOK.md`'s "stale negatives" section
   for when it's still worth re-checking a rejection.
4. **No fabrication.** If a plausible-sounding organization/claim can't be
   backed by a real, checkable URL, it doesn't go in the dataset — flag it
   in `research/world_country_checklist.csv` as a gap instead.
